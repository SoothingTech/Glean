# 5.7.3 六大模块接口设计

> 本小节是 5.7.1（外部接口）与 5.7.2（内部接口）的展开：把 5.7.1 的端点归位到六个模块，并补齐每个模块的 **REST 契约 / Java 门面 / 领域事件 / 兼容约束**。
>
> **硬约束**：本节不新增表、不删除/不改名已有字段、不改 5.4.2 现有事件的名字与语义、不占用或复用已废弃的错误码。兼容承诺是"**对已有客户端只增不删**"：允许新增列（可空或有默认值）、新增事件、占用本模块段空位的新码；越出本节范围的联动改动一律登记到 5.7.3.10 的回写项，不在正文里"偷偷改"。凡与既有设计冲突之处，以 5.6—5.8 为准。标注 **【新增】** 的接口是本节补充的，属于**只增不改**，不影响既有客户端。

## 5.7.3.1 通用约定

### 依赖方向（与 5.2.3 一致，ArchUnit 守护）

```
account ◀── ingest ◀── task ◀── plan ◀── remind
                        │        │        │
                        └────────┴────────┘
                                 ▼
                              view（只读）
```

- 上游只能通过 **Facade 接口 + 领域事件** 使用下游，禁止跨模块访问对方表。
- `view` 只读：只订阅事件、只调 `*QueryFacade`，不发布任何事件、不产生写操作。
- `account` 被所有模块依赖，自己不依赖任何业务模块（只依赖 `common-*`）。

### 同步调用与事件的通道纪律（本节新增，全节遵守）

同一业务事实**只允许一个权威通道**，另一条若存在只能是"通知"，且消费方必须幂等。判据：**要返回值、要在调用方事务内完成的用 Facade；一对多、可最终一致的用事件。**

| 业务事实                   | 权威通道                            | 发起方                         | 其他模块如何得知                        |
| -------------------------- | ----------------------------------- | ------------------------------ | --------------------------------------- |
| 授权级别/范围变更          | 事件 `ConsentChanged`             | account 发布                   | ingest/task/remind/view 订阅（account **不**反向调业务模块） |
| 任务确认                   | 事件 `TaskConfirmed`              | task 发布                      | plan 求解、view 失效                    |
| 任务终态（完成/取消/过期） | 事件 `TaskClosed` **【新增】**    | task 发布                      | plan 释放时段、remind 注销、view 失效    |
| 排程结果（含重排、改期）   | 事件 `PlanGenerated`              | plan 发布                      | remind 注册、view 失效                  |
| 用户主动排程（拖拽/重排）  | Facade `SchedulingFacade`         | plan 的 REST 层同步调用        | 结果仍以 `PlanGenerated` 广播           |
| 只读查询                   | Facade `*QueryFacade`             | view / controller 同步调用     | 不广播                                  |

> 本节已按此纪律删除三条重复通道：`ConsentFacade.onRevoked`、`ReminderFacade.onPlanChanged`、`SchedulingFacade.release`。禁止同一动作既发事件又调 Facade；但"命令走 Facade、命令产生的事实再广播事件"（如 `replan` → `PlanGenerated`）属于两个事实，不算双通道。
>
> **事件投递可靠性**：跨模块领域事件均通过"业务写库 + 本地消息表（Transactional Outbox）"或事务提交后投递机制兜底（见 5.4 / 5.11），保证至少一次送达，消费端统一按 `eventId` 幂等。

### 统一信封与分页

```json
{ "code": "0", "message": "ok", "data": { }, "traceId": "0af7651916cd43dd" }
```

- 状态码分两层，**5.8.1 的 HTTP 列是唯一权威**，本节不再另行解释：
  - **协议/传输语义**用真实 HTTP 状态：认证失败 401（E5001）、无权限/授权不足 403（E5002/E5005）、资源不存在 404、版本/状态/幂等冲突 409（E5003/E5004/E2006）、超体积 413（E1002）、限流 429（E9003）；
  - **显式业务异常**用 HTTP 200 + `code` 非 0：需客户端感知并提示或引导处理的业务错误，如抽取失败（E2xxx）、排程无解（E3001）、提醒失败（E4xxx）等；
  - **静默降级 / 内部观测码**用 HTTP 200 + `code` 为 `"0"`：接口正常返回 `data`，由 `data` 内状态字段表达业务态（如 `deduped: true`、`status: TIMEOUT`）；对应的 `E1003`（去重）、`E3002`（排程超时）、`E4002`（围栏超限静默）等仅作服务端日志与监控指标编码，不进入外层 `code`。
  - 客户端按 **HTTP 状态 + `code`** 两维判定：4xx 原则上只做"重试 / 跳登录 / 刷新"，不弹业务文案（**409 冲突除外**：允许客户端在刷新实体的同时展示轻量状态变化提示，如 `E2006`）；显式业务文案一律读 `code`。
- 列表分页统一游标：`?cursor=<serverTs>_<id>&limit=50`，响应带 `nextCursor`（与 5.11.2 的 `serverTs + id` 游标一致）。
- 写接口幂等：`Idempotency-Key` 请求头，Redis 键 `idem:{userId}:{key}`，TTL 24 h；同键不同载荷返回 `E5004`。

### 枚举单一来源：接口取 `code`、落库取 `db`、展示取 `label`

枚举值会同时出现在五处：Java 枚举、数据库 `CHECK`、前端常量、CSV/ICS 导出、事件载荷。为防漂移，**`contract/enums.json` 是唯一来源**，每条枚举固定三列：

- `code`：**接口、事件、导出、筛选参数只用它**（英文大写，稳定、不随文案改）；
- `db`：落库值，与 5.6.2 的 `CHECK` 逐字一致（`task.type` 是中文，其余沿用 code）；
- `label`：展示文案，只进前端 i18n 包，**不得出现在任何契约里**。

```json
{
  "TaskType": [
    {"code": "PICKUP", "db": "取件", "label": "取件"},
    {"code": "PAYMENT", "db": "缴费", "label": "缴费"},
    {"code": "BOOKING", "db": "预约", "label": "预约"},
    {"code": "RETURN", "db": "归还", "label": "归还"},
    {"code": "APPOINTMENT", "db": "约定", "label": "约定"}
  ],
  "TaskStatus": [
    {"code": "CANDIDATE", "db": "CANDIDATE", "label": "候选"},
    {"code": "PENDING_CONFIRM", "db": "PENDING_CONFIRM", "label": "待确认"},
    {"code": "CONFIRMED", "db": "CONFIRMED", "label": "已确认"},
    {"code": "SCHEDULED", "db": "SCHEDULED", "label": "已排程"},
    {"code": "DONE", "db": "DONE", "label": "已完成"},
    {"code": "CANCELLED", "db": "CANCELLED", "label": "已取消"},
    {"code": "EXPIRED", "db": "EXPIRED", "label": "已过期"}
  ]
}
```

其余枚举按同一结构补全：

| 枚举 | `code`（接口/事件/导出） | `db`（落库） | `label`（展示） |
| ---- | ---- | ---- | ---- |
| SourceType | QQ / WECHAT / MANUAL / NOTIFY | 同 code | QQ / 微信 / 手动 / 通知 |
| TriggerType | TIME / GEOFENCE / PRECONDITION / RELATED | 同 code | 时间 / 地点 / 前置条件 / 关联 |
| Channel | PUSH / LOCAL / CALENDAR_ONLY | 同 code | 推送 / 本地 / 仅日历 |
| ReminderResult | SENT / SUPPRESSED / FAILED / IGNORED / DONE | 同 code | 已发送 / 已抑制 / 失败 / 已忽略 / 已完成 |
| SolveStatus | OPTIMAL / FEASIBLE / TIMEOUT / INFEASIBLE | 同 code | 最优 / 可行 / 超时 / 无解 |
| ViewKind | calendar / card / gantt / map / table | 同 code | 日历 / 卡片 / 甘特 / 地图 / 表格 |
| DegradedReason | PLAN_INFEASIBLE / PLAN_CONFLICT / LLM_TIMEOUT / RULE_ONLY / ESTIMATED_DISTANCE | 同 code | 见 5.8.2 |
| ConsentLevel | L0 / L1 / L2 / L3 / L4 | 同 code | 关闭 / 手动投递 / 机器人会话 / 通知感知 / 附件语音 |

生成与校验（构建期，任一步失败即阻断）：

1. 注解处理器生成 Java 枚举：`@JsonValue` 输出 `code()`，MyBatis 由 `AttributeConverter` 写 `db()`——**同一个枚举禁止两套输出方式**；
2. Flyway 的 `CHECK` 文本由 `db` 列**生成**（不是解析 SQL 反比对），约束变更与 `enums.json` 永远同一次提交；
3. 前端脚本生成 `constants/*.ts`（`code` + `label`），生成后 `git diff --exit-code` 检出漂移。

> 这样"落库按 db、接口一律 code、前端按 label 渲染"三者同时成立，`type` 与 `status` 也不会再一个中文一个英文。

## 5.7.3.2 账号与授权（glean-account）

**边界**：只管"你是谁、你能开哪一级采集、你做过什么"，不碰任务与消息内容。

### 对外 REST

| 方法   | 路径                                        | 说明                                                                     | 幂等 |
| ------ | ------------------------------------------- | ------------------------------------------------------------------------ | ---- |
| POST   | `/api/v1/auth/login`                      | 手机号+验证码换 JWT，返回 `accessToken`/`refreshToken`/`expiresIn` | —   |
| POST   | `/api/v1/auth/refresh`                    | 刷新令牌                                                                 | —   |
| POST   | `/api/v1/auth/logout` **【新增】**  | 注销当前设备，令牌入黑名单（Redis，TTL=剩余有效期）                      | 幂等 |
| GET    | `/api/v1/consent`                         | 当前授权级别与范围                                                       | —   |
| PUT    | `/api/v1/consent`                         | 调整级别 L0—L4，`raise` 立即生效、`lower` 触发撤回流程              | 幂等 |
| GET    | `/api/v1/devices` **【新增】**      | 设备列表（含 `lastSeenAt`、`platform`）                              | —   |
| DELETE | `/api/v1/devices/{id}` **【新增】** | 远程下线                                                                 | 幂等 |
| GET    | `/api/v1/audit`                           | 本人审计记录，游标分页                                                   | —   |

**PUT /consent 请求**（`scope` 与 `consent.scope` jsonb 同构）：

```json
{
  "level": "L3",
  "scope": {
    "notifyApps": ["com.tencent.mm", "com.taobao.taobao"],
    "qqGroups": ["123456789"],
    "quietHours": ["23:00", "07:00"]
  },
  "clientRequestId": "c-8f21"
}
```

**响应**：返回调整后的级别与**撤回影响面**（供前端提示"将断开 2 个群、停止 3 个应用的通知"）：

```json
{ "code": "0", "data": { "level": "L3", "revoked": { "groups": 2, "apps": 3 }, "effectiveAt": "2026-11-18T18:00:03+08:00" } }
```

### 对内 Facade

```java
public interface ConsentFacade {
    ConsentLevel currentLevel(UUID userId);
    boolean atLeast(UUID userId, ConsentLevel required);          // 不足抛 E5005
}

public interface TokenFacade {
    AuthPrincipal verify(String bearer);                          // 失败抛 E5001
    String issue(UUID userId, String deviceId);
}
```

- `atLeast` 由 `ingest`/`task`/`remind`/`view` 在入口处调用，**授权判断只在此处**，不在各模块重复写 if。
- **撤回不走 Facade**：`account` 不得依赖任何业务模块（5.2.3），因此没有 `onRevoked`。撤回由 `ConsentChanged` 一对多广播：ingest 断采集、task 清未确认候选（10 s 内，5.3.7）、remind 注销围栏、view 失效缓存。
- 顺序不靠"调用先后"，靠事件里的 `changedAt` 作**撤回水位**：消费端记录每个用户最后生效的水位，丢弃 `changedAt < 水位` 的迟到事件（Redis Stream 至少一次 + 乱序的兜底）。
- 撤回广播默认纯异步；若产品强要求 `PUT /consent` 返回前"采集侧已停"，由 API 层在发布事件后**仅定向等待 `ingest` 模块的 ack**（≤1 s，不等待全量订阅方，避免 API 层耦合订阅方数量）；超时只记告警指标并由补偿任务重试，**不因此改响应结构、也不允许让 account 反向调用 ingest**。

### 事件

| 方向 | 事件               | 说明                                                                              |
| ---- | ------------------ | --------------------------------------------------------------------------------- |
| 发布 | `ConsentChanged` | 载荷 `{userId, fromLevel, toLevel, scope, changedAt}`，`ingest` / `task` / `remind` / `view` 订阅 |
| 订阅 | —                 | 无                                                                                |

### 兼容约束

- JWT claims 固定为 `sub / dev / lvl / iat / exp`，`lvl` 变更时旧 token 不追溯，靠 `atLeast` 实时查库兜底。
- `consent.level` 只增不减语义：**升级累进**（L3 必然含 L2 能力），代码里不得出现"L4 才可 L2 操作"的散落判断。

## 5.7.3.3 采集接入（glean-ingest）

**边界**：把五种入口收敛成一个 `IngestedMessage`，做完清洗/去重/初筛就交棒，**不做抽取**。

### 适配器 SPI（新增一源不改主流程）

```java
public interface MessageSourceAdapter {
    SourceType type();                                  // QQ / WECHAT / MANUAL / NOTIFY
    boolean supports(RawPayload payload);
    IngestedMessage parse(RawPayload payload);          // 只做结构映射，不做业务判断
    void ack(MessageRef ref);                           // 回调确认（OneBot/iLink 需要）
}
```

注册表 `Map<SourceType, MessageSourceAdapter>` 由 Spring 收集全部实现，**新增来源 = 加一个实现类 + `enums.json` 补一条 `SourceType`，管道代码零改动**；枚举本身仍由生成器一次性改全 Java/CHECK/前端，别写成"零改动"。

### 对外 REST

| 方法 | 路径                                          | 说明                                         | 幂等                   |
| ---- | --------------------------------------------- | -------------------------------------------- | ---------------------- |
| POST | `/api/v1/ingest/manual`                     | 文本/图片(multipart)/语音转写文本            | `Idempotency-Key`    |
| POST | `/api/v1/ingest/notification`               | 端侧批量上报（≤50 条/批）                   | `Idempotency-Key`    |
| POST | `/api/v1/ingest/bot/qq`                     | OneBot 回调（支持反向 WS 与 HTTP 上报）      | 按 `message_id` 去重 |
| POST | `/api/v1/ingest/bot/wechat`                 | iLink 回调                                   | 按 `msgid` 去重      |
| GET  | `/api/v1/ingest/sources` **【新增】** | 适配器在线状态（供设置页展示"机器人已离线"） | —                     |

**核心 DTO**（字段与 `message_fragment` 一一对应）：

```java
public record IngestedMessage(
    UUID userId,
    SourceType sourceId,
    String conversationId,
    String senderId,          // 已脱敏
    String text,              // ≤500 字，超长截断并记 E1002/E9001
    String attachmentKey,     // MinIO 键，可空
    OffsetDateTime capturedAt
) {}
```

**响应**（三态，客户端据此决定是否提示）：

```json
{ "code": "0", "data": { "messageId": "m-...", "deduped": false, "prefiltered": true, "accepted": true } }
```

- `deduped=true` → 命中指纹，`code` 仍为 `0`，内部计 `E1003`（静默）；
- `prefiltered=false` → 未命中待办特征，仍入库但不投递 `MessageIngested`（5.1.1 的"D1 丢弃路径"）。

### 对内 Facade

```java
public interface IngestFacade {
    IngestResult ingest(IngestedMessage message, IdempotencyKey key);
}

public interface MessageQueryFacade {                 // 供 task/view 溯源
    Optional<MessageFragment> byId(UUID messageId);
    List<MessageFragment> byConversation(UUID userId, String conversationId, int limit);
}
```

### 事件

| 方向 | 事件                | 载荷                                                                      |
| ---- | ------------------- | ------------------------------------------------------------------------- |
| 发布 | `MessageIngested` | `{messageId, userId, sourceType, text, fingerprint}`，与 5.4.2 完全一致 |
| 订阅 | `ConsentChanged`  | 降级时断开对应适配器、清空群白名单                                        |

### 兼容约束

- `source_id`（varchar(16)）落库与接口都取 `code`：`QQ / WECHAT / MANUAL / NOTIFY`；"微信/手动/通知"这类展示文案来自 `label`，不进接口。新增来源必须走 `enums.json` → Java/`CHECK`/前端的一次性生成。
- 指纹算法**冻结为 v1**：`"fp:v1:" + hex(sha256(join('\u0001', source_id, sender_id, 归一化文本)))`，字段间用 `\u0001` 分隔（防 `("ab","c")` 与 `("a","bc")` 的拼接碰撞），归一化顺序见 5.12.2；前缀带版本号，将来升级可双写比对，不必猜历史数据。
- 去重是**时间窗**不是永久：Redis `SETNX` 5 分钟为主，库侧兜底查询用 `created_at >= now() - interval '5 min'`；因此 5.6.2 的 `uq_fragment_fp` **要从唯一约束降为普通索引**（只改索引、不改字段），否则同一句话（如"记得取快递"）下周再发会被永久静默丢弃（E1003）。
- 附件键格式 `user_id/yyyyMM/uuid.ext`，删除任务时按前缀级联删对象（5.3.2）。

## 5.7.3.4 任务中心（glean-task）

**边界**：把消息变成带置信度的任务，管状态机与溯源；**不做排程**、**不做提醒**。

### 对外 REST

| 方法  | 路径                                    | 说明                                                               | 幂等                     |
| ----- | --------------------------------------- | ------------------------------------------------------------------ | ------------------------ |
| GET   | `/api/v1/tasks`                       | 筛选（status/type/时间区间）+ 游标分页                             | —                       |
| GET   | `/api/v1/tasks/{id}`                  | 详情，含 `evidence` 与原文片段                                   | —                       |
| PATCH | `/api/v1/tasks/{id}`                  | 编辑字段，`If-Match: {version}`                                  | 乐观锁 `E5003`         |
| POST  | `/api/v1/tasks/{id}/confirm`          | 确认入库（PENDING_CONFIRM → CONFIRMED），`If-Match: {version}`  | 幂等 + 乐观锁 `E5003`  |

| POST  | `/api/v1/tasks/{id}/undo`             | 撤销自动入库（5 min 内）                                           | 幂等                     |
| POST  | `/api/v1/tasks/batch`                 | 批量确认/忽略/改期（≤50 条）                                      | `Idempotency-Key`      |

> `confirm / done / cancel` 与 `PATCH` 一致，通过 `If-Match: {version}` 透传给 Facade 的 `expectedVersion` 做并发校验；已处于目标态时重复提交按幂等成功返回，非法状态流转由 `TaskStateMachine` 抛 `E2006`（409）。

**TaskDTO**（组合自 `task` / `message_fragment` / `plan`，不造新字段；`degradedReason` 落 `task.degraded_reason`，5.6.2 只增列）：

  "title": "领取快递",
  "type": "PICKUP",
  "windowStart": "2026-11-16T08:00:00+08:00",
  "windowEnd": "2026-11-16T21:00:00+08:00",
  "deadline": "2026-11-16T18:00:00+08:00",
  "placeId": "p-7",
  "confidence": 0.91,
  "status": "SCHEDULED",

  "sourceMessageId": "m-...",
  "source": {
    "messageId": "m-...",
    "text": "周五下午三点前到菜鸟驿站取下快递，取件码 8-2-1234",

    "planId": "p-9",

| 方向 | 事件                                 | 载荷                                                                          |
| ---- | ------------------------------------ | ----------------------------------------------------------------------------- |
| 发布 | `TaskExtracted`                    | `{taskId, confidence, status}`                                              |
| 发布 | `TaskConfirmed`                    | `{taskId, taskVersion}`                                                     |
| 发布 | `TaskClosed` **【新增】** | `{taskId, status, reason, taskVersion}`，`status ∈ DONE / CANCELLED / EXPIRED`；覆盖全部终态，`plan`/`remind`/`view` 据此释放时段、注销提醒、失效缓存 |
| 订阅 | `MessageIngested`                  | 触发抽取编排                                                                  |
| 订阅 | `PlanConflicted`                   | **不改 status**（避免非法迁移）：置 `degraded_reason=PLAN_CONFLICT`，`plan` 留空，冲突项随详情返回 |
| 订阅 | `ConsentChanged`                   | 降级时清理未确认候选（按 `changedAt` 水位丢弃迟到事件）                       |

> `TaskClosed` 是本节对 5.4.2 的**唯一新增事件**（原设想的 `TaskCancelled` 已并入，不再单独存在），用"一个事件 + `status` 判别"取代按状态拆三个事件，避免"完成/过期漏释放"。

### 兼容约束

- 阈值 `0.85 / 0.60` 来自配置中心（5.9），**代码里不得硬编码**；`conf` 公式见 5.3.3，权重若要调整必须同步更新评测基线。
- `evidence` 的 `span` 必须落在原文区间内，越界判 `E2002`（5.12.1），前端据 span 高亮。
- `task.type` 落中文 `db` 值（`ck_task_type`），接口/事件/导出传 `code`（`PICKUP`），Jackson 与 MyBatis 各用一个输出器——见 5.7.3.1。

## 5.7.3.5 排程引擎（glean-plan）

**边界**：只做"把任务放进时间表并给理由"，不生成任务、不发提醒。

### 对外 REST

| 方法 | 路径                        | 说明                                  | 幂等                |
| ---- | --------------------------- | ------------------------------------- | ------------------- |
| GET  | `/api/v1/plans?from=&to=` | 区间日程（含 `reason`、`solver`） | —                  |
| POST | `/api/v1/plans/replan`    | 单任务或全量重排                      | `Idempotency-Key` |
| POST | `/api/v1/plans/{id}/move` | 拖拽改期，`If-Match: {version}`     | 乐观锁              |

**重排请求**（`scope=SINGLE` 只重解当天，对应 5.12.3 的增量重排）：

```json
{ "scope": "SINGLE", "taskId": "t-1024", "reason": "USER_MOVE" }
```

### 对内 Facade（与 5.7.2 同名同形，仅补返回细节）

```java
public interface SchedulingFacade {
    ScheduleResult solve(ScheduleRequest request);         // 预算 1000 ms
    ScheduleResult replan(ScheduleRequest request, ReplanScope scope);
}
```

- `solve/replan` 是**请求/响应型**调用，由 plan 自己的 REST 层使用；跨模块的"取消/完成释放时段"走 `TaskClosed` 事件，**不再暴露 `release`**（同一动作不留第二条通道）。

**ScheduleRequest / ScheduleResult**（与 5.7.2 的排程服务契约同构，Java 侧只是镜像）：

```java
record ScheduleRequest(UUID userId, int budgetMs, List<TaskInput> tasks,
                       List<BusySlot> busy, Prefs prefs) {}

record ScheduleResult(SolveStatus status,                 // OPTIMAL/FEASIBLE/TIMEOUT/INFEASIBLE
                      List<PlanItem> plans,               // taskId, start, end, reason
                      Objective objective,                // {travel, span, late}
                      List<UUID> conflictTaskIds) {}
```

### 事件

| 方向 | 事件               | 载荷                                     |
| ---- | ------------------ | ---------------------------------------- |
| 发布 | `PlanGenerated`  | `{planId, taskId, start, end, reason}` |
| 发布 | `PlanConflicted` | `{taskId, conflictTaskIds}`            |
| 订阅 | `TaskConfirmed`  | 触发求解                                 |
| 订阅 | `TaskClosed`     | 按 `taskId` 释放时段（`DONE` / `CANCELLED` / `EXPIRED` 一视同仁） |

### 兼容约束

- `solver` 枚举固定 `CP_SAT / GREEDY`，写入 `plan.solver`；**不得**因换求解器而改字段。
- `objective` 的键固定 `travel / span / late`（与 5.3.4 的 w1/w2/w3 对应），新增目标只能加键，不能改名。
- 一任务多版本：**旧行**写 `superseded_by = 新行.id`（字段义为"被谁取代"），`GET /plans` 默认只返回 `superseded_by is null` 的行；重排在同一个事务里"插入新行 → 回填旧行"，并加部分唯一索引 `unique (task_id) where superseded_by is null` 保证一个任务只有一个当前版本（5.6.2 只增索引，不改字段）。
- 求解超时**不是错误**（`status=TIMEOUT` + `code=0`），仅内部计 `E3002`。

## 5.7.3.6 提醒服务（glean-remind）

**边界**：只负责"什么时候、通过什么渠道、把哪条提醒发出去"，不判断任务该不该做。

### 对外 REST

| 方法 | 路径                                                       | 说明                                                               | 幂等                |
| ---- | ---------------------------------------------------------- | ------------------------------------------------------------------ | ------------------- |
| GET  | `/api/v1/reminders?taskId=&from=&to=` **【新增】** | 提醒记录（含 `result`）                                          | —                  |
| POST | `/api/v1/reminders/{id}/ack` **【新增】**          | 端侧确认已展示 / 完成 / 忽略（写 `result`）                      | 幂等                |
| POST | `/api/v1/reminders/{id}/snooze` **【新增】**       | 延期（客户端传绝对时间 `snoozeUntil`，如 +15 min / 明天，重注册触发器） | `Idempotency-Key` |

> 用户点通知直接完成任务的场景，客户端调 `POST /tasks/{id}/confirm` 或 `/done` 仍走任务中心；`ack` 只回写提醒结果，避免两处都能改任务状态。

### 对内 Facade

```java

    // 跨模块不直接调用：注册由 PlanGenerated、注销由 TaskClosed 事件驱动；
    // 保留该接口供 remind 内部处理器与补数脚本使用，必须按 (taskId, type, fireAt) 幂等。
    void register(ReminderSpec spec);      // 时间/地点/前置/关联四类
    void cancel(UUID taskId);
}

record ReminderSpec(UUID taskId, TriggerType type, OffsetDateTime fireAt,
                    String placeId, Integer radiusM, Channel channel) {}
```

### 事件

| 方向 | 事件               | 载荷                                      |
| ---- | ------------------ | ----------------------------------------- |
| 发布 | `ReminderFired`  | `{reminderId, taskId, channel, result}` |
| 订阅 | `PlanGenerated`  | 注册时间/地点触发（权威通道，不再额外调 `onPlanChanged`） |
| 订阅 | `TaskClosed`     | 任务完成/取消/过期时注销该任务的全部提醒              |
| 订阅 | `TaskConfirmed`  | 前置条件触发                              |
| 订阅 | `ConsentChanged` | L3 撤回时注销全部围栏（按 `changedAt` 水位丢弃迟到事件）   |

### 兼容约束

- `trigger_type / channel / result` 三组枚举固定（5.6.2），抑制规则参数全部来自 5.9 配置（`remind.max_per_task_per_day` 等），**不得写死 2 次/3 次**。
- 地点触发只注册"未来 24 h、3 km 内"的围栏，超出走 `E4002` 静默 + 服务端兜底（5.3.5）。
- 同一 POI 同小时的提醒合并，合并后仍保留各自 `reminder` 行（`result=SUPPRESSED`），便于统计忽略率。

### 错误码归属（在 5.8.1 基础上只补不占）

| 段位  | 归属模块   | 已定义       | 本节补充                     |
| ----- | ---------- | ------------ | ---------------------------- |
| E1xxx | 采集接入   | E1001–E1004 | —                           |
| E2xxx | 任务中心   | E2001–E2005 | **E2006 非法状态迁移** |
| E3xxx | 排程引擎   | E3001–E3003 | —                           |
| E4xxx | 提醒服务   | E4001–E4004 | —                           |
| E5xxx | 账号与授权 | E5001–E5005 | —                           |

### 四条"不破"规则

1. **DTO 只增字段**：删除/改名字段 = 破坏契约；确需废弃时保留字段并标 `@Deprecated`，两个版本后再删，且先用 `enums.json` 与 JSON Schema 校验。
2. **事件只加不改**：事件名与语义冻结（5.4.2），新增字段追加在载荷尾部；消费者开启 `FAIL_ON_UNKNOWN_PROPERTIES=false`，按 `eventId` 幂等。
3. **库表只加不删**：Flyway 向前兼容，删列必须先停用一个版本；`CHECK` 约束变更与 `enums.json` 同一次提交。
4. **接口版本**：全部挂在 `/api/v1`，破坏性变更开 `/api/v2`，v1 至少保留一个大版本。

### 契约测试（进 CI，与 5.2.3 的 ArchUnit 同一道门）

| 测试                  | 作用                                                                    |
| --------------------- | ----------------------------------------------------------------------- |
| ArchUnit              | 六模块依赖方向、view 不得有写操作、`ai-*`/`common-*` 不依赖业务模块 |
| Spring Cloud Contract | Facade 调用方与实现方的请求/响应同源校验                                |
| JSON Schema 校验      | 抽取结果、事件载荷、`/views` 响应结构                                 |
| 枚举一致性            | `enums.json` ↔ Flyway `CHECK` ↔ 前端常量                          |
| 迁移回归              | 在空库 + 上一版快照各跑一遍 `flyway migrate`                          |
